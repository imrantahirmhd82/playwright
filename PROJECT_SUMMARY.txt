--------------------------------------------------------------------------------

                   (^7.0.2), CommonJS modules, strict mode

                   automationexercise.com requirements
- Execution      : Serial (workers: 1), headless, 120s test / 10s expect timeout
- CI/CD          : GitHub Actions (ubuntu-latest, Node LTS), retries in CI

3. PAGE OBJECT MODEL (POM) DESIGN
--------------------------------------------------------------------------------
BasePage (abstract)
  - constructor(protected readonly page: Page)
  - waitAfterAction(): fixed 400ms settle wait after interactions (x2 calls)
  - verifyTitle(): expect(page).toHaveTitle(/Automation Exercise/)
  - All page classes hold Playwright locators (getByRole, getByText, data-qa
    attributes, CSS) as class properties or getter methods, and expose
    async business-flow methods (open, fill, submit, verify*).

Page classes and their responsibilities:

  Homepage (Homepage.ts)
    - open(), verifyLoggedInAs(name) -> "Logged in as {name}" visible

  SignupPage (SignupPage.ts)
    - openSignupForm(), startSignup(name, email), login(email, password)
    - completeRegistration(details) - account info + address + create
    - continueAfterAccountCreation(name?) - Account Created + logged-in checks
    - accountInfoVisible() - OR assertion: "Enter Account Information" OR
      "Email Address already exist!"
    - deleteAccount() - "Account Deleted!" verification

  ProductsPage (ProductsPage.ts)
    - open(), search(term), addProduct(id), addFirstVisibleProduct()
    - openProductDetails(id), openFirstProductDetails(),
      openFirstVisibleProductDetails()
    - openCategory(id), openBrand(name), openTshirtsCategory()
    - verifyLoggedInAs(name), cart modal open/close handling

  CartPage (CartPage.ts)
    - open(), ensureProductInCart(), verifyProduct(id) - #product-{id}
    - proceedToCheckout(), expectReview(productId) - review row visible
    - cart marker visibility assertions

  CheckoutPage (CheckoutPage.ts)
    - verifyTitle() -> URL /checkout/, verifyAddressDetails(),
      verifyOrderReview(), verifyProduct(id)
    - Invoice download flow (used by TC24)

  ContactUsPage (ContactUsPage.ts)
    - open(), fillForm(details), submitAndAcceptConfirmation()
    - Verifies GET IN TOUCH heading, field values (toHaveValue),
      submit button visible + enabled, handles native JS dialog
      (type === 'confirm', message === 'Press OK to proceed!')

  ReviewPage (ReviewPage.ts)
    - submit(reviewText) - #review-form visible, alert-success text
      "Thank you for your review."
    - addRecommendedProduct() - carousel add-to-cart + cart modal class check
    - expectLoaded()

  ScrollPage (ScrollPage.ts)
    - openAndScrollToFooter() - footer visible assertion
    - scrollToTopWithArrow() / scrollToTopWithoutArrow()

  SubscriptionPage (SubscriptionPage.ts)
    - subscribe(email), expectSuccess() ->
      "You have been successfully subscribed!"

  TestCasesPage (TestCasesPage.ts)
    - openFromHeader(), openFromHero()
    - URL /test_cases/ + "test cases" heading visible

9. OBSERVATIONS / TALKING POINTS FOR THE ARCHITECT
--------------------------------------------------------------------------------
1. Hybrid assertion placement: ~42 expects live inside page objects
   (verify*/expect* methods) while flow-level expects stay in specs. Worth
   discussing: should all assertions live in specs, or is encapsulated
   page-level verification acceptable?
2. Fixed waits: BasePage.waitAfterAction() uses waitForTimeout(400) (and is
   called twice in sequence). Preferred Playwright practice is web-first
   assertions with auto-retrying locators instead of hard sleeps.
3. Serial execution (workers: 1): chosen for stability against a shared live
   site with ads; trade-off is total suite duration. Parallel-safe design
   (unique users via getUniqueRegistrationData) already partially exists.
4. Empty reserved folders: config/ and fixtures/ exist but contain no files
   (tsconfig still includes them) - candidates for custom fixtures/global
   setup or removal.
5. Legacy folders: tests/Login/ and tests/Product/ are unnumbered strays
   alongside the canonical 01-13 numbered folders - candidates for cleanup
   or migration.
6. Flakiness strategy: live-site ads are handled by adHandler, navigation
   retries by gotoWithRetry, CI retries=2, trace on first retry, and
   video/screenshot on failure - a layered defense against a non-deterministic
   target.
7. Test data: Excel as the single source of truth with write-back support
   (saveRegistrationData) and unique-user generation; alternative would be
   JSON/YAML fixtures or Playwright's built-in data handling.
8. Reporters: dual reporter setup (github for PR annotations + html for
   humans) demonstrates CI-aware configuration via process.env.CI.
9. Only 6 npm scripts exist while there are 13 feature folders - consider a
   parameterised script (e.g. npm test -- --grep or folder args) for the rest.
